# Solutions for: Select overnight orchestration tool (Attractor pillar)

Problem: prob-20260405-001

## Variants (5)

### V1. OpenHands (headless CLI + V1 event-sourcing)

Standalone autonomous coding platform. Docker sandbox per workspace, event-sourced V1 architecture with append-only event log enabling pause/resume/crash-recovery. CLI headless mode with --json JSONL output. Model-agnostic via LiteLLM (100+ providers including Anthropic, Google, DeepSeek, OpenRouter). Action-Execution-Observation tool pattern. Best-documented production/VPS headless path in the research corpus. Supports sub-agent delegation.

**Strengths:**
- Strongest crash recovery (event-sourced, replay from any point)
- Best trace output (structured JSONL event stream)
- Widest model flexibility (LiteLLM, 100+ providers)
- Most documented headless/VPS deployment path
- Lowest assembly — pull-and-configure

**Weakest link:** Resource footprint: Docker-in-Docker sandbox + agent process consumes 1.5-2.5GB RAM. On a budget VPS (4-8GB) coexisting with Mockoon container, memory pressure risks silent degradation or OOM during 10h run. Also: always-approve mode = full trust, no native cost cap — safety limits must come from external wrapper or Leash pillar.

**Risks:**
- Docker-in-Docker resource pressure on budget VPS
- Security advisories (CVE-2026-33718, pickle/CWE-502)
- No native cost/iteration limits — need external wrapper
- Full-trust headless mode needs Leash pillar compensation

**Stepping stone:** yes — opens future possibilities

### V2. Ralph Orchestrator (hat-based fresh-context loop)

Lightweight orchestrator implementing repeated fresh-context agent runs via EventLoop. Hat-based personas (design, implement, test, review) with per-hat model backends. File-based state (.agent/events.jsonl + scratchpad.md). Native safety: max_cost_usd, max_iterations, max_runtime_seconds. Philosophy of disk-is-state, git-is-memory (v2 removed SQLite). Designed explicitly for overnight unattended runs. Drives external CLI agents (e.g. Claude API, any agent CLI).

**Strengths:**
- Lightest resource footprint (bash loop + one process, <500MB)
- Best native safety limits (cost, iterations, runtime caps built in)
- Fresh-per-cycle context — directly combats context drain
- Per-hat model routing (expensive tasks to capable models, cheap to fast)
- Simplest architecture (files + git, no DB or containers)

**Weakest link:** Single-agent sequential execution — no parallelism. If the task graph has independent branches, they execute serially. Also: no automatic crash recovery — files survive but re-launch is manual. No Docker sandbox — isolation must come from Leash pillar.

**Risks:**
- No auto-resume on crash — manual restart needed
- No sandbox — Leash pillar must compensate
- Single-agent sequential limits parallelism for v2
- Less community validation than OpenHands

**Stepping stone:** yes — opens future possibilities

### V3. CrewAI (role-based agents with Flows)

Python framework for role-based multi-agent crews. Sequential or hierarchical process management. Flows for event-driven/stateful orchestration. YAML agent/task definitions. Task guardrails and retries. Configurable per-agent model backends. Good natural mapping to the pillar architecture (Coder crew, Tester crew, Reviewer crew). Enterprise features (SSO/RBAC in v1.13+).

**Strengths:**
- Role-based model maps naturally to pillar architecture
- Multi-agent with hierarchical delegation
- Task guardrails and retry logic built in
- Good composability story for v2 expansion
- YAML configuration is readable and auditable

**Weakest link:** Reliability of long-running autonomous loops — third-party reports flag unstable loops. Framework provides building blocks but overnight VPS reliability requires custom checkpointing, supervision, and restart logic that you build yourself. More assembly than OpenHands or Ralph for the specific overnight use case.

**Risks:**
- Third-party reports of unstable long-running loops
- Custom checkpointing/recovery needed for overnight
- More assembly required than standalone orchestrators
- Time-to-first-run is days not hours for reliable overnight setup

**Stepping stone:** yes — opens future possibilities

### V4. oh-my-openagent (phased orchestration on OpenCode)

Plugin for OpenCode providing phased orchestration: Intent gate, Sisyphus task manager, Prometheus planner, Atlas executor, category-specific subagents. Ralph-loop continuation with <promise>DONE</promise> and default 100 iterations. Non-interactive CLI mode via bunx oh-my-openagent run. Task system with dependencies and parallel-ready tasks in .sisyphus/tasks/ JSON. Best conceptual phase model in the field.

**Strengths:**
- Best phased orchestration model (Intent/Sisyphus/Prometheus/Atlas)
- Task system with dependencies and parallel-ready architecture
- Ralph-loop continuation built in
- Active development with recent PRs

**Weakest link:** Maturity and reproducibility: dev branch as default, naming migration (oh-my-opencode to oh-my-openagent), breaking config changes (#2823). Debug log goes to /tmp/ (ephemeral). Weakest trace/audit output of all finalists. Risk of debugging the orchestrator instead of testing the overnight flow during the pilot.

**Risks:**
- Dev branch default — reproducibility risk
- Naming migration and breaking config changes
- Ephemeral debug log (/tmp/) — weak audit trail
- Hook-level permissions only, not OS-level command interception
- Momus judges plans not outcomes — no post-hoc scenario scoring

### V5. Ruflo/claude-flow (daemon + smart routing, Claude Code dependency)

NPM orchestration layer on Claude Code. Background daemon with PID file, headless workers, swarm topologies. Notable for 3-tier smart routing: WASM (free) for simple edits, cheaper models for medium tasks, expensive models for complex work. Claims 250% Claude Code usage extension. Vector memory (HNSW), session hooks. BUT: requires Claude Code CLI (claude --headless). User has Claude Code Pro (not Max). v3 alpha stability.

**Strengths:**
- Smart 3-tier routing genuinely reduces cost (WASM/Haiku/Sonnet/Opus)
- Daemon architecture fits VPS overnight pattern
- Anti-drift coordinator for multi-worker topology
- Vector memory for cross-session context

**Weakest link:** Hard dependency on Claude Code CLI availability and subscription. Claude Code Pro usage caps are tight (user confirms it runs out quickly). Smart routing helps extend usage but does not eliminate the dependency. If Anthropic changes CLI access or pricing, the orchestrator breaks. v3 alpha stability adds risk for unattended overnight runs.

**Risks:**
- Claude Code Pro runs out quickly — may not sustain 10h overnight
- v3 alpha stability for unattended use
- If Anthropic restricts CLI access, entire orchestrator breaks
- Overlap risk with native Claude Code features over time

## Non-Dominated Set

**Pareto front:** OpenHands, Ralph

**Selection policy:** For the weekend pilot: optimize for resource fit on budget VPS (<$150 AUD/mo total), native safety limits (hard cost cap critical at this budget), and context drain resistance (user-stated concern). Accept weaker crash recovery since pilot goal is learning, not production SLA. Between the two non-dominated options, Ralph wins on the pilot-critical axes (footprint, safety, context drain) while OpenHands wins on dimensions more valuable at v2 scale (crash recovery, trace richness, parallelism).

**Recommended:** Ralph
