# Solutions for: Select Judge tool for overnight autonomous coding pilot

Problem: prob-20260406-003

## Variants (4)

### V1. V1. OpenJudge (py-openjudge)

Open-source Python evaluation framework from AgentScope-AI. 50+ built-in graders, custom LLMGrader with template variables ({scenario}, {execution_trace}), FunctionGrader for deterministic checks, SimpleRubricsGenerator for scenario-specific rubrics, GradingRunner for batch evaluation. Returns GraderScore (score float + reason string + metadata dict). Official Langfuse and LangSmith integrations. Supports any OpenAI-compatible model via OpenAIChatModel. Install: pip install py-openjudge. Pure Python library, no infrastructure.

**Strengths:**
- Native LLMGrader accepts arbitrary template variables — {scenario} + {execution_trace} maps directly to our use case
- FunctionGrader allows deterministic checks (e.g., stdout == 'SATISFIED') alongside LLM scoring
- Official Langfuse integration for fetching traces and writing scores back
- GradingRunner for batch/concurrent evaluation with progress tracking
- TrajectoryComprehensiveGrader built-in for agent execution trace evaluation
- pip install — no Docker, no database, no infrastructure

**Weakest link:** Project maturity and canonical source ambiguity — if the maintainers fragment or deprecate the PyPI package name, we'd need to fork or migrate

**Risks:**
- Relatively new project (2025-2026) — API may still be evolving
- Two GitHub orgs host it (agentscope-ai vs modelscope) — canonical source unclear from research
- LangChain-adjacent model abstraction (BaseChatModel) adds a thin dependency layer

**Stepping stone:** yes — opens future possibilities

**Rollback:** Swap judge/ directory implementation back to raw OpenAI calls. GraderScore output is a superset of our JSON schema, so downstream consumers (morning review) don't change.

### V2. V2. Dify (full LLM app platform as judge)

Open-source LLM application platform with visual workflow builder, RAG, agent capabilities, model management. Would require deploying the full Dify stack (Postgres, Redis, Celery workers, web server) and building a workflow via UI or API that accepts scenario+trace and returns a score. No Python SDK (only Node.js/PHP). Interaction via REST API calls. Research consensus: 'overkill for a lightweight judge component.'

**Strengths:**
- Visual workflow builder could make judge logic visible/editable by non-developers
- Full model management with multiple provider support
- Active large community (30k+ GitHub stars)

**Weakest link:** Infrastructure weight — deploying and maintaining a full application platform to run a single post-execution scoring call is architecturally mismatched

**Risks:**
- Massive infrastructure overhead: Postgres + Redis + Celery + web server + workers just for scoring
- No Python SDK — requires HTTP API calls from our Python judge script, adding latency and failure modes
- Redundant orchestration layer alongside Ralph + CrewAI
- Operational burden: database migrations, service health monitoring, version upgrades for a component that runs once per overnight cycle

**Rollback:** Tear down Docker Compose stack. Replace HTTP API calls with direct Python LLM calls.

### V3. V3. AgentScope eval framework (custom metrics + judge functions)

Developer-centric multi-agent framework from Alibaba. Evaluation is a first-class area: Task, Metric, Evaluator, Storage abstractions. Judge functions follow JudgeType signature (task dict + response + auxiliary models → JudgeOutput with reward float). RayEvaluator for distributed eval with OpenTelemetry tracing. However: NO built-in LLM judge implementations — users must write their own judge functions and custom metrics. The framework provides infrastructure for evaluation orchestration but not pre-built graders. Documented path to richer judging is to use OpenJudge as an extension.

**Strengths:**
- First-class evaluation architecture with clean abstractions (Task, Metric, Evaluator, Storage)
- Distributed evaluation via RayEvaluator with OTEL tracing
- Strong corporate backing (Alibaba/ModelScope)
- Documented integration path WITH OpenJudge for pre-built graders

**Weakest link:** No pre-built LLM judging — AgentScope provides the plumbing but explicitly requires the user to implement all scoring logic, which is exactly what OpenJudge already packages

**Risks:**
- No built-in LLM judge — must write all scoring logic from scratch
- Ray dependency for distributed eval adds infrastructure weight
- Framework is designed for RL-style agent training, not post-hoc scenario satisfaction scoring
- Tutorial only shows basic string matching judge, not scenario-based LLM evaluation
- Using AgentScope's eval without OpenJudge means we're building the same thing OpenJudge already provides

**Rollback:** Remove agentscope dependency. Replace with direct LLM calls or OpenJudge.

### V4. V4. Build-yourself harness (custom Python + OpenAI SDK)

No product — assemble from the StrongDM principles and build-yourself-one.md research. Write a custom Python script that reads scenario markdown + trace text, constructs an LLM prompt, calls gpt-4o-mini via openai SDK, parses JSON response with satisfied/score/reasoning. This is essentially what pilot_judge.py in the plan already implements. Zero dependencies beyond openai SDK. Full control over prompt, schema, retries. No framework overhead. The current plan already has this implemented in Task 6.

**Strengths:**
- Zero framework overhead — just openai SDK (already a project dependency)
- Full control over prompt engineering, retry logic, output parsing
- Already partially implemented in the plan (pilot_judge.py is ~50 lines)
- No learning curve — team already understands the code
- Easiest to debug and modify

**Weakest link:** Extensibility ceiling — works perfectly for a single scenario but scaling to 10+ scenarios with multiple grading dimensions, batch evaluation, and observability integration means reimplementing what OpenJudge already provides

**Risks:**
- No structured grader abstractions — each new grading dimension requires hand-coding
- No batch evaluation runner — must build concurrency yourself
- No Langfuse integration out of the box — must write score write-back manually
- No trajectory-aware evaluation patterns — must parse agent traces manually
- Maintenance burden shifts entirely to us — no upstream fixes or improvements
- No rubric generation, no template engine, no multi-dimensional scoring framework

**Stepping stone:** yes — opens future possibilities

**Rollback:** Already the baseline — nothing to roll back to.
