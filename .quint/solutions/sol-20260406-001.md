# Solutions for: Select orchestration tool for overnight autonomous coding (Attractor pillar)

Problem: prob-20260406-001

## Variants (10)

### V1. V1. OpenHands (headless CLI + event-sourced sandbox)

Standalone autonomous coding platform from All-Hands AI. Docker sandbox per workspace, event-sourced V1 architecture with append-only event log enabling pause/resume/crash-recovery. CLI headless mode (openhands --headless) with --json JSONL output. Model-agnostic via LiteLLM (100+ providers). Action-Execution-Observation pattern. Best-documented production/VPS headless deployment path in the research corpus. Supports sub-agent delegation. SDK + remote Agent Server for Docker/K8s/VM deployment.

**Strengths:**
- Strongest crash recovery (event-sourced, replay from any point)
- Best trace output (structured JSONL event stream, directly parseable by judge)
- Widest model flexibility (LiteLLM, 100+ providers including Anthropic/DeepSeek/OpenRouter)
- Most documented headless/VPS deployment path in the entire research corpus
- Lowest assembly — pull-and-configure with documented quick-start

**Weakest link:** Resource footprint: Docker-in-Docker sandbox + agent process consumes 1.5-2.5GB RAM. On a 4GB VPS (Hetzner CX22) coexisting with Mockoon container, memory pressure risks silent degradation or OOM during 10h runs. Also: always-approve headless mode = full trust with no native cost/iteration cap — safety must come from external wrappers or Leash pillar.

**Risks:**
- Docker-in-Docker resource pressure may cause OOM on 4GB VPS during 10h run
- Security advisories (CVE-2026-33718, pickle/CWE-502) — needs hardening review
- No native cost/iteration limits — budget enforcement requires external wrapper
- Full-trust headless mode means Leash pillar must compensate for safety

**Stepping stone:** yes — opens future possibilities

### V2. V2. Ralph Orchestrator (hat-based fresh-context loop)

Lightweight orchestrator implementing repeated fresh-context agent runs via EventLoop. Hat-based personas (design, implement, test, review) with per-hat model backends. File-based state (.agent/events.jsonl + scratchpad.md). Native safety: max_cost_usd, max_iterations, max_runtime_seconds. Philosophy of disk-is-state, git-is-memory (v2 removed SQLite). Designed explicitly for overnight unattended runs. Drives external CLI agents (Claude API, Gemini CLI, Q Chat, ACP-compliant agents).

**Strengths:**
- Lightest resource footprint (bash loop + one process, <500MB RAM)
- Best native safety limits (max_cost_usd, max_iterations, max_runtime_seconds built in)
- Fresh-per-cycle context — core philosophy directly combats context drain
- Per-hat model routing (expensive models for complex tasks, cheap for simple ones)
- Simplest architecture (files + git, no DB or containers to maintain)

**Weakest link:** Single-agent sequential execution — no parallelism. If the task graph has independent branches, they execute serially. No automatic crash recovery — files survive but re-launch is manual. No Docker sandbox — isolation must come from Leash pillar.

**Risks:**
- No auto-resume on crash — manual restart needed, lose remaining hours
- No sandbox — Leash pillar must compensate for command isolation
- Single-agent sequential limits future parallelism for v2
- Smaller community than OpenHands — less validation at scale

**Stepping stone:** yes — opens future possibilities

### V3. V3. CrewAI (role-based agents with Flows)

Python framework for role-based multi-agent crews. Sequential or hierarchical process management. Flows for event-driven/stateful orchestration with decorators (@start(), @listen()). YAML agent/task definitions. Task guardrails and retries. Configurable per-agent model backends. Enterprise features (SSO/RBAC in v1.13+). Flow modeled as Pydantic BaseModel for serialization.

**Strengths:**
- Role-based model maps naturally to pillar architecture (Coder/Tester/Reviewer crews)
- Multi-agent with hierarchical delegation built in
- Task guardrails and retry logic
- Good composability story for v2 expansion
- YAML configuration is readable and auditable

**Weakest link:** Overnight reliability of long-running autonomous loops — third-party reports flag unstable loops. Framework provides building blocks but overnight VPS reliability requires custom checkpointing, supervision, and restart logic that you build yourself. Time-to-first-run is days not hours for a reliable overnight setup.

**Risks:**
- Third-party reports of unstable long-running autonomous loops
- Custom checkpointing/recovery needed for overnight — significant glue code
- Time-to-first-run is days not hours for reliable overnight setup
- Enterprise features (SSO/RBAC) are premature overhead for solo pilot

**Stepping stone:** yes — opens future possibilities

### V4. V4. AG2/AutoGen (group chat + LangGraph persistence)

Community-driven continuation of Microsoft AutoGen. ConversableAgent, LLMConfig, and run()/process() two-step pattern for programmatic control. Group Chat for multi-agent collaboration. Official LangGraph cookbook for graph-backed state and checkpointing. pip install ag2[openai]. Python >=3.10.

**Strengths:**
- Group chat critic loop matches broader-fix architecture pattern
- Official LangGraph integration for graph state and checkpointing
- Microsoft-backed community with good documentation
- Run/process two-step pattern allows programmatic control before execution

**Weakest link:** No standalone headless runner — you build the overnight harness yourself around AG2's agent primitives. AG2 provides conversation patterns, not an execution environment. LangGraph integration adds checkpointing but also adds LangChain dependency stack complexity. Time-to-first-run is days: significant integration coding required.

**Risks:**
- No standalone execution environment — you build the harness
- LangGraph dependency adds complexity (LangChain family packages)
- Time-to-first-run is days of integration coding
- No native safety limits — must wrap externally

**Stepping stone:** yes — opens future possibilities

### V5. V5. Deer Flow (ByteDance SuperAgent harness)

Open-source MIT-licensed SuperAgent harness from ByteDance. Orchestrates multiple sub-agents with Docker sandboxed execution. Parallel sub-agents for decomposed tasks. Progressive skill loading for token cost management. Python-centric with TypeScript support. BYO API key (no DeerFlow subscription). Memory file + DB suggestion for persistence.

**Strengths:**
- Parallel sub-agents for decomposed tasks
- Docker sandbox for isolated execution
- Progressive skill loading reduces token costs
- BYO API key, no subscription
- MIT license, backed by ByteDance engineering

**Weakest link:** Maturity gap between marketing narrative and operational readiness for headless overnight runs. No documented headless CLI path — deployment is DIY on VM. Star counts and releases in blogs are time-sensitive and unverified. Persistence story is 'memory file + DB suggestion' not 'production checkpoint system'.

**Risks:**
- No documented headless/VPS deployment path — DIY assembly required
- Persistence is 'memory file + DB suggestion', not production-grade checkpoint
- Blog metrics (stars, claims) need verification against actual repo state
- Relatively new — less community validation for overnight autonomy use case

**Stepping stone:** yes — opens future possibilities

### V6. V6. AgentFlow (Stanford Flow-GRPO research line)

Academic research system from Stanford: modular Planner/Executor/Verifier/Generator coordinated via memory. Flow-GRPO (flow-based group refined policy optimization) addresses long-horizon sparse reward credit assignment. ICLR 2026 oral. arXiv 2510.05592. Research code repo exists but is a training/optimization system, not an operational orchestrator.

**Strengths:**
- Best theoretical decomposition model (Planner/Executor/Verifier)
- Flow-GRPO addresses long-horizon credit assignment — valuable ideas
- ICLR 2026 oral — strong academic validation
- Verification loop concept aligns with Judge pillar

**Weakest link:** This is a research contribution (training methodology + paper + models), not an operational tool. No CLI, no deployment path, no trace output, no safety limits. Using it as an orchestrator requires building everything from scratch around the research ideas. Fundamentally different category from the other candidates.

**Risks:**
- Research system, not operational tool — no CLI, no headless mode
- Would require building entire orchestrator from scratch around ideas
- Time-to-first-run is weeks/months, not hours
- Name collision with vendor 'agent flow' UIs causes confusion

### V7. V7. Gas Town (Yegge multi-agent orchestrator)

Go-based MIT-licensed multi-agent orchestration system by Steve Yegge. Mayor/workers/merge roles. Git-backed persistence with worktrees. Tmux session management. Designed for 20-30 concurrent agents. Town wall security concept. Agents spawn with only the context they need and resolve when done, minimizing context drain.

**Strengths:**
- Context drain resistance — agents spawn with minimal context and resolve
- Git-backed persistence with worktrees for isolation
- Town wall security concept
- Designed for scale (20-30 concurrent agents)
- Strong philosophical alignment with StrongDM Attractor pattern

**Weakest link:** Claude Code dependency — designed around Claude Code CLI as the agent backend. Cost tracking issue (#24) shows tmux pane capture cannot reliably read Claude Code cost UI, leading to $0.00 reporting. Anecdotal spend of ~$200/month for 10 hours of use. Parallelism is the value prop, but pilot is single-scenario — paying complexity cost without parallelism benefit.

**Risks:**
- Claude Code dependency violates BYO-API-key constraint unless provider integration confirmed
- Cost tracking broken (issue #24, tmux pane capture)
- Parallelism value prop wasted on single-scenario pilot
- Anecdotal $200/month spend for 10h — may exceed budget
- Go binary requires compilation for deployment

**Stepping stone:** yes — opens future possibilities

### V8. V8. oh-my-openagent (phased orchestration on OpenCode)

Plugin for OpenCode providing phased orchestration: Intent gate, Sisyphus task manager, Prometheus planner, Atlas executor, category-specific subagents. Ralph-loop continuation with <promise>DONE</promise> and default 100 iterations. Non-interactive CLI via bunx oh-my-openagent run. Task system with dependencies and parallel-ready tasks in .sisyphus/tasks/ JSON.

**Strengths:**
- Best conceptual phased model (Intent/Sisyphus/Prometheus/Atlas)
- Task system with dependencies and parallel-ready architecture
- Ralph-loop continuation built in
- Active development with recent PRs (PR #1348 on context strategies)

**Weakest link:** Maturity and reproducibility: dev branch as default, naming migration (oh-my-opencode to oh-my-openagent, issue #2823, PR #2417), breaking config changes. Debug log goes to /tmp/ (ephemeral on reboot). Weakest trace/audit output of all candidates. Risk of debugging the orchestrator instead of testing the overnight flow during pilot.

**Risks:**
- Dev branch default — reproducibility risk for pilot
- Naming migration and breaking config changes add friction
- Ephemeral debug log (/tmp/) — weak audit trail
- Hook-level permissions only, not OS-level command interception
- Momus judges plans not outcomes — no post-hoc scenario scoring

### V9. V9. Ruflo/claude-flow (daemon + smart routing)

NPM orchestration layer on Claude Code. Background daemon with PID file, headless workers, swarm topologies. Notable 3-tier smart routing: WASM (free) for simple edits, cheaper models for medium tasks, expensive models for complex work. Claims 250% Claude Code usage extension. Vector memory (HNSW), session hooks. npm install @claude-flow/cli.

**Strengths:**
- Smart 3-tier routing genuinely reduces cost (WASM/Haiku/Sonnet/Opus)
- Daemon architecture fits VPS overnight pattern naturally
- Anti-drift coordinator for multi-worker topology
- Vector memory (HNSW) for cross-session context retention

**Weakest link:** Hard dependency on Claude Code CLI availability and subscription. User has Claude Code Pro (not Max) which runs out quickly. Smart routing helps extend usage but does not eliminate the Claude Code dependency. If Anthropic changes CLI access or pricing, the orchestrator breaks. v3 alpha stability adds risk for unattended overnight runs.

**Risks:**
- Claude Code Pro runs out quickly — may not sustain 10h overnight
- v3 alpha stability for unattended production use
- If Anthropic restricts CLI access, entire orchestrator breaks
- Overlap risk with native Claude Code features over time
- Issue #1335: scheduler not firing, metrics not updating — check fix status

### V10. V10. Agent Flywheel/ACFS (NTM + MCP mail + CASS)

Skills/integrations ecosystem for Agentic Coding Flywheel Setup. NTM (Named Tmux Manager) for parallel tmux panes with dashboards. MCP Agent Mail for async inter-agent coordination (inbox/outbox, threading, file leases). CASS memory system. Combines multiple tools rather than being a single orchestrator. Easiest reported setup.

**Strengths:**
- NTM provides strong Leash + audit (policy YAML, ntm safety check)
- MCP Agent Mail enables async inter-agent coordination
- Easiest reported setup per user notes
- File reservation leases prevent agent conflicts

**Weakest link:** Not a single orchestrator — it's an ecosystem of coordination tools (NTM + MCP mail + skills). You still need an underlying coding agent CLI for each tmux pane (Claude Code, Cursor, etc.). Adds coordination layer but doesn't replace the need for an orchestration spine. Lacks built-in judge and cost controls.

**Risks:**
- Not a standalone orchestrator — coordination layer over other agent CLIs
- Still pays for underlying agent CLI subscriptions
- No built-in judge or cost controls
- Multiple moving parts (NTM + MCP mail + CASS) increase surface area

**Stepping stone:** yes — opens future possibilities

## Non-Dominated Set

**Pareto front:** V1, V2

**Selection policy:** For the weekend pilot, optimize for: (1) resource fit on budget VPS with 4GB RAM — eliminates Heavy footprint candidates, (2) native safety limits with hard cost cap — essential at $10/pilot budget without time to build external wrappers, (3) time-to-first-run in hours not days — pilot is this Saturday. Accept weaker crash recovery since pilot goal is learning, not production SLA. Between the two non-dominated options: Ralph (V2) wins on the three pilot-critical axes (footprint, safety, context drain) while OpenHands (V1) wins on dimensions more valuable at v2 scale (crash recovery, trace richness, model breadth). V6 (AgentFlow research) eliminated as categorically different (research, not tool). V7 (Gas Town) and V9 (Ruflo) eliminated by single-provider-lock constraint violation (Claude Code dependency). V10 (Agent Flywheel) eliminated as not a standalone orchestrator.
