# Solutions for: Select Memory pillar for overnight autonomous coding v1

Problem: prob-20260406-007

## Variants (4)

### V1. V1. mcp-memory-service (sqlite_vec first)

Adopt mcp-memory-service as the primary memory pillar in local sqlite_vec mode for v1, with optional hybrid/cloud sync deferred. Use it as shared persistent memory service for retrieval and continuity across runs.

**Strengths:**
- Service-oriented memory with retrieval APIs aligned to agent workflows
- Local-first mode reduces external dependency risk
- Good fit for unattended operation and centralized memory access across components

**Weakest link:** Operational complexity creep if deployment expands beyond minimal local mode too early

**Risks:**
- Broader configuration/runtime surface than file-only memory
- Hybrid/cloud options can add credential and operational complexity
- Potential overreach if too many advanced features are enabled early

**Stepping stone:** yes — opens future possibilities

**Rollback:** Disable advanced modes and fall back to simpler local memory path or alternate candidate while preserving memory export backups.

### V2. V2. Acontext skill-file memory

Adopt Acontext as primary memory pillar using skill-file memory artifacts with tool-driven retrieval and high inspectability.

**Strengths:**
- Memory artifacts are human-readable/editable, improving auditability
- Strong portability concept (memory as files/skills)
- Good conceptual fit for explicit memory hygiene and review

**Weakest link:** Retrieval quality depends on consistent skill structuring and disciplined agent tool usage

**Risks:**
- Additional platform/runtime components beyond pure local file usage can add ops complexity
- Retrieval relies on tool-mediated progressive disclosure and agent discipline
- Production fit for this exact stack requires integration validation

**Stepping stone:** yes — opens future possibilities

**Rollback:** Fall back to service-style retrieval layer if run-time retrieval consistency is insufficient.

### V3. V3. Beads as primary memory layer (work graph)

Use Beads as the main memory pillar centered on graph-based work-state, dependencies, and issue lifecycle.

**Strengths:**
- Excellent execution-memory model for tasks/dependencies
- Strong fit for multi-run workflow continuity and blocker-aware progression
- CLI-native workflows can be efficient for agent operations

**Weakest link:** Scope mismatch: work-memory strength does not fully cover semantic/knowledge memory needs

**Risks:**
- Not a complete semantic long-term memory solution by itself
- Couples process strongly to Beads task model
- May require complementary knowledge memory layer anyway

**Stepping stone:** yes — opens future possibilities

**Rollback:** Re-scope Beads as complementary execution memory while moving primary long-term memory to service/file candidate.

### V4. V4. YAMS local content-addressed memory substrate

Use YAMS as the local memory substrate emphasizing dedupe, snapshots, and hybrid search across corpus data.

**Strengths:**
- Powerful local-first storage and retrieval primitives
- Strong for corpus-centric memory and versioned content history
- Low external lock-in in local operation

**Weakest link:** Experimental maturity risk for unattended overnight production behavior

**Risks:**
- Project labels itself experimental (higher stability risk)
- More suitable as substrate than full memory governance product
- Plugin/config churn can impact unattended reliability

**Stepping stone:** yes — opens future possibilities

**Rollback:** Keep in non-critical lane until stability confidence is proven; fallback to more mature primary option.
