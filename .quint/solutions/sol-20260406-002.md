# Solutions for: Select DTU/Mocks tool for overnight autonomous coding pilot

Problem: prob-20260406-002

## Variants (4)

### V1. Mockoon CLI/Docker

Static file-defined HTTP mock server. Routes authored in Mockoon Desktop GUI or hand-written JSON, served headlessly via CLI or Docker image (mockoon/cli). Already prototyped in pilot plan with compose file and mockoon-pilot.json. Routes are static: defined at startup from a JSON data file, no runtime modification API. Supports response templating (Handlebars), CORS, latency simulation, proxy mode. MIT licensed.

**Strengths:**
- Simplest possible setup: single JSON file + 3-line compose
- Already prototyped in current pilot plan — zero switching cost for v1
- GUI for authoring routes (Mockoon Desktop) lowers barrier for non-programmers
- MIT license, active community (~6k GitHub stars)
- Supports response templating via Handlebars helpers
- Official Docker image, well-documented CLI flags

**Weakest link:** No programmatic runtime API — agent cannot create or modify stubs during execution; all routes must be predefined in the JSON data file before container start

**Risks:**
- No runtime API for dynamic stub creation — agent cannot modify mocks programmatically during a run
- Routes are static: must restart container to change mock definitions
- No record/replay capability — all mocks must be hand-written
- No native MCP or agent integration

**Rollback:** Trivial: remove compose file and JSON data file, replace with alternative

### V2. WireMock standalone + WireMock MCP

Java-based HTTP mock server with rich matching, response templating, fault injection, record/replay, and stateful behavior. Runs standalone as Docker container (wiremock/wiremock). Key differentiator: WireMock MCP server exists for AI coding agent integration — agents can create, modify, and query stubs via MCP tool calls. Also has a REST Admin API for dynamic stub CRUD at runtime without restart. Supports recording real API traffic and replaying. Apache 2.0 licensed.

**Strengths:**
- REST Admin API: agent can create/modify/delete stubs at runtime via HTTP POST to /__admin/mappings
- WireMock MCP: purpose-built MCP server for AI agent workflows — agents can manage mocks via tool calls
- Record/replay: can capture real API traffic and generate stubs automatically
- Rich request matching (URL, headers, body, JSON path, regex), response templating, fault/delay injection
- Stateful scenarios: model multi-step API interactions (e.g., order lifecycle)
- Massive community (~6.4k stars), battle-tested in enterprise
- Official Docker image, well-documented

**Weakest link:** JVM memory footprint — running alongside orchestrator, sandbox, and other pilot containers on a budget VPS (Hetzner CX22: 4GB RAM) means ~200-400MB for WireMock is a meaningful fraction of available resources

**Risks:**
- JVM-based: heavier memory footprint than Go/Node alternatives (~200-400MB idle vs ~50MB)
- More configuration surface area than Mockoon — steeper initial learning curve
- WireMock MCP is relatively new; maturity and documentation may lag behind core
- Startup time slightly longer due to JVM warmup

**Stepping stone:** yes — opens future possibilities

**Rollback:** Replace Docker image and mapping files; REST API stub format differs from Mockoon JSON but concept is same

### V3. Hoverfly (Go proxy/simulate)

Lightweight Go binary that operates as an HTTP proxy. In 'capture' mode, records real API traffic to simulation files (JSON). In 'simulate' mode, replays recorded responses. Can also serve hand-written simulations. Docker image available. Key strength is the proxy-first model: point your app's HTTP client at the Hoverfly proxy and it intercepts transparently. REST Admin API for runtime management. Apache 2.0 licensed.

**Strengths:**
- Extremely lightweight: Go binary, ~30-50MB memory idle
- Proxy-first model: transparent interception without changing target URLs (just set HTTP_PROXY)
- Capture/simulate: record real API traffic, export as simulation JSON, replay deterministically
- REST Admin API for runtime simulation switching and state inspection
- Fault/latency injection (middleware concept)
- Good Docker support, fast startup

**Weakest link:** Proxy-based model requires HTTP_PROXY env var cooperation from all clients — if the agent's code or tools bypass proxy settings, mocks are silently skipped with no error signal

**Risks:**
- Proxy model requires HTTP_PROXY configuration — some tools/agents may not respect proxy env vars
- Less rich request matching than WireMock (no JSON path matchers, simpler templating)
- Smaller community than WireMock/Mockoon (~2.4k stars)
- No MCP integration — agent interacts via REST API or file-based simulations
- Documentation less polished than WireMock/Mockoon

**Stepping stone:** yes — opens future possibilities

**Rollback:** Remove proxy config, switch to direct-URL mock server approach

### V4. Mountebank (multi-protocol imposters)

Node.js-based mock server supporting HTTP, HTTPS, TCP, and SMTP protocols via 'imposters'. Stubs are created dynamically via REST API (POST to /imposters). Each imposter binds to a port and serves predefined responses. Supports response injection (JS functions), predicates for matching, behaviors for decoration. Designed for dynamic stub creation — the REST API is the primary interface, not static files. MIT licensed.

**Strengths:**
- REST API is the primary interface: POST /imposters creates stubs dynamically — ideal for agent-driven mock creation
- Multi-protocol: HTTP, HTTPS, TCP, SMTP in one process — future-proof for non-HTTP dependencies
- Response injection: JS functions can generate dynamic responses
- Lightweight Node.js process, reasonable memory footprint (~80-120MB)
- Well-documented REST API with good examples
- Can save/restore imposter state for reproducibility

**Weakest link:** Community activity and maintainer bandwidth — fewer recent releases and contributions compared to WireMock and Mockoon; risk of stagnation for an architectural dependency

**Risks:**
- Older project (~3.5k stars, less active than WireMock/Mockoon in recent years)
- No record/replay from real traffic — stubs must be programmatically defined
- No MCP integration
- TCP/SMTP capabilities unlikely needed for our pilot — complexity without immediate value
- Documentation style is dense/academic

**Rollback:** Replace Docker image and imposter definitions; API-first approach means mock definitions live in agent code, not external files
