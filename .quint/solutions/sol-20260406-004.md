# Solutions for: Select Observability tool for overnight autonomous coding pipeline

Problem: prob-20260406-004

## Variants (5)

### V1. V1. Langfuse self-hosted (full platform)

Deploy Langfuse via Docker Compose (Postgres, ClickHouse, Redis, MinIO, Langfuse server + worker). Instrument Ralph's agent execution loop to emit traces via the Langfuse Python SDK or OTEL exporter. Each overnight session gets a sessionId; LLM calls become GENERATION observations; tool invocations (git, pytest, shell) become TOOL observations. Morning review uses Langfuse's web UI: filter by session, browse trace tree, see per-call cost/tokens, annotate findings. Built-in LLM-as-judge evals available but deferred to avoid overlap with OpenJudge. Batch export (JSONL) feeds OpenJudge for authoritative verdicts.

**Strengths:**
- Purpose-built LLM observability UI with session grouping, trace trees, cost dashboards
- Per-call and per-session token/cost tracking computed automatically from provider responses
- Built-in annotation system for morning review (thumbs up/down, categorical, numeric scores)
- OTEL ingest endpoint means OpenLLMetry or any OTEL source can feed it later without platform change
- MIT licensed, fully self-hosted, no trace data leaves your infrastructure
- Agent Graph View for visualizing execution paths as graphs (LangGraph-style)
- Prompt management with version tracking and trace-to-prompt-version linkage
- Batch export enables feeding trace bundles to OpenJudge without duplicating judge logic

**Weakest link:** Infrastructure resource contention — Langfuse's 4-5 container stack (especially ClickHouse) competing for RAM on a 4 GB VPS with the agent workload is the most likely failure mode during the pilot

**Risks:**
- Infrastructure footprint: 4-5 containers consuming ~1.5-2 GB RAM idle on a 4 GB VPS
- ClickHouse is memory-hungry; may OOM under pressure with agent + WireMock + Ralph on same host
- Version alignment: SDK v3 OTEL-native features require sufficiently new Langfuse server images
- Automation triggers limited to 'prompt' events — no webhook on trace ingestion yet
- Built-in LLM-as-judge could create confusion about authority vs OpenJudge if accidentally enabled

**Stepping stone:** yes — opens future possibilities

**Rollback:** Stop Langfuse containers; traces remain in Ralph events.jsonl. Reverse is trivial — Langfuse is read-path only.

### V2. V2. OpenLLMetry SDK + Jaeger all-in-one

Add OpenLLMetry Python SDK (traceloop-sdk) to the orchestrator wrapper. Auto-instruments OpenAI/Anthropic calls; manually decorate shell/git commands with @tool. Export OTEL spans to a Jaeger all-in-one container (single binary: collector + query + UI). Morning review uses Jaeger UI: trace waterfall, span search, service map. No LLM-specific views — prompts visible as span attributes but no cost rollup, no session grouping, no annotation.

**Strengths:**
- Lightweight infrastructure: 1 additional container (Jaeger all-in-one ~200-400 MB RAM)
- Auto-instrumentation for LLM providers, CrewAI, MCP tool calls out of the box
- Standards-based: OTEL spans are portable to any backend later
- Jaeger UI provides serviceable trace waterfall and search
- Can migrate to Langfuse later by changing the OTEL exporter endpoint (no re-instrumentation)

**Weakest link:** No LLM-aware review surface — Jaeger renders generic OTEL spans without semantic understanding of prompts, responses, cost, or session structure, making morning review significantly less productive than purpose-built LLM observability

**Risks:**
- No LLM-aware UI: prompts/responses are buried in span attributes, not rendered as conversations
- No per-call cost tracking — tokens are in attributes but USD cost is not computed or displayed
- No session-level aggregation — overnight runs are just 'a bunch of traces', not a reviewable session
- No annotation system — morning review is browse-only, no way to mark findings or score quality
- Shell/git commands require manual @tool decoration — not auto-instrumented
- Jaeger UI is designed for microservice debugging, not LLM application review

**Stepping stone:** yes — opens future possibilities

**Rollback:** Remove traceloop-sdk; stop Jaeger container. Traces in Jaeger are ephemeral (in-memory by default) unless configured with persistent storage.

### V3. V3. OpenLLMetry SDK + OTLP file exporter (no backend)

Add OpenLLMetry SDK to instrument LLM calls. Export OTEL spans to local JSONL files using the OTEL FileLogExporter. No backend service — traces are files on disk alongside Ralph's events.jsonl. Morning review is jq/grep over OTEL JSON. Post-pilot, replay files into any OTLP backend.

**Strengths:**
- Zero additional infrastructure — no containers beyond the existing stack
- OTEL-standard format: files can be replayed into Langfuse, Jaeger, Grafana Tempo later
- Auto-instrumentation captures LLM calls without code changes
- Minimal resource consumption — just a Python library, no background services
- Files are git-friendly and can be committed as trace artifacts

**Weakest link:** No review surface at all — the tool captures structured data but provides no way to browse, filter, or annotate it, reducing morning review to reading JSON files, which is only marginally better than reading raw logs

**Risks:**
- Morning review is reading raw OTEL JSON with jq — no UI, no filtering, no annotation
- No cost/token aggregation — raw span attributes only
- No session grouping beyond filename conventions
- Shell/git commands still need manual @tool decoration
- File-based traces accumulate without automatic rotation or cleanup
- Effectively 'observability without the observe part' — data capture without a review surface

**Stepping stone:** yes — opens future possibilities

**Rollback:** Remove traceloop-sdk. Files remain on disk.

### V4. V4. Ralph JSONL only (no additional tooling)

Rely entirely on Ralph orchestrator's native events.jsonl output plus OpenJudge verdict JSON. No additional observability tool. Morning review: read events.jsonl with jq, read judge JSON, read git diff. This is the baseline — what happens if we add nothing.

**Strengths:**
- Zero integration effort — already decided and built into the pilot plan
- Zero infrastructure cost — no additional containers or RAM
- Zero additional complexity — nothing to configure, maintain, or debug
- Events.jsonl captures phase transitions, tool invocations, iteration counts, cost limits
- Git diff provides the definitive 'what changed' artifact

**Weakest link:** No LLM-level visibility — Ralph logs orchestrator events (iterations, hat switches, cost caps) but not the underlying LLM calls (which model, which prompt, how many tokens, what cost), making cost diagnosis and quality improvement impossible without external tooling

**Risks:**
- No structured LLM-specific data: no per-call tokens, no prompt/response capture, no cost tracking
- No UI — morning review is grep/jq over log files
- No session aggregation — each run is a flat stream of events
- Cannot diagnose 'why did the agent spend $12 on this run?' without manual log archaeology
- Does not scale: 50-scenario nightly runs produce unmanageable log volumes without structured querying
- No annotation — findings from morning review are not captured in a reusable format

**Rollback:** N/A — this is the baseline. Nothing to roll back.

### V5. V5. Langfuse self-hosted with phased deployment (pilot-deferred)

Designate Langfuse as the Observability tool but deploy in two phases. Phase 1 (pilot): use OpenLLMetry SDK with OTLP file exporter — captures structured LLM traces to disk with zero infra overhead. Ralph JSONL + file traces + OpenJudge verdict serve the morning review. Phase 2 (post-pilot): deploy Langfuse on a dedicated host or upgraded VPS, replay Phase 1 file traces into it, switch the OTEL exporter from file to Langfuse's OTLP endpoint. This separates the architectural decision (Langfuse) from the deployment timeline (after pilot validates the loop).

**Strengths:**
- Pilot runs on zero additional infrastructure — file exporter only
- Architectural decision is locked now: Langfuse is the target, not a maybe
- Phase 1 file traces are OTEL-standard and can be replayed into Langfuse retroactively
- Phase 2 deployment can size infrastructure correctly based on pilot trace volume data
- OpenLLMetry instrumentation is write-once: same decorators/auto-instrument work for both phases
- Avoids the 4 GB RAM contention risk entirely during the pilot
- Post-pilot Langfuse deployment inherits all the V1 strengths (UI, cost, sessions, annotation)

**Weakest link:** Deferred value — the full observability experience (Langfuse UI, cost dashboards, annotation) is not available during the pilot, which is precisely when you most need to learn what morning review should look like

**Risks:**
- Phase 1 morning review is still file-based (same weakness as V3 during pilot)
- Two-phase approach means the full review experience is deferred — pilot learnings about 'what I need from morning review' come from degraded tooling
- Risk of Phase 2 never happening if pilot is 'good enough' with files
- Slightly more integration work: install OpenLLMetry now, configure Langfuse later

**Stepping stone:** yes — opens future possibilities

**Rollback:** Phase 1: remove traceloop-sdk, files remain. Phase 2: stop Langfuse containers, keep file exports as fallback.

## Non-Dominated Set

**Pareto front:** V1, V5

**Selection policy:** Pilot-safety-first with post-pilot ceiling: Among non-dominated variants, prefer the one that (a) does not risk pilot failure through resource contention, (b) locks the highest-ceiling architectural direction, and (c) preserves all data captured during the pilot for retroactive analysis. V4 is dominated by V3 (V3 adds structured LLM data for zero infra cost). V3 is dominated by V5 (V5 adds a concrete Phase 2 path to LLM-aware UI). V2 is dominated by V5 (V5 achieves the same pilot infra profile as V2 without Jaeger's generic UI limitations, and reaches Langfuse-grade review post-pilot). V1 and V5 form the Pareto front: V1 wins on immediate morning review quality, V5 wins on pilot infra safety. Under pilot-safety-first policy, V5 is selected — it avoids the 4 GB RAM contention risk while locking Langfuse as the architectural target. The 'deferred value' weakness (Phase 1 morning review is file-based) is acceptable because the pilot's primary goal is validating the loop, not optimizing the review experience.

**Recommended:** V5
