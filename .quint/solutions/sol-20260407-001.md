# Solutions for: Execution sandbox pillar for overnight autonomous coding

Problem: prob-20260407-001

## Variants (3)

### V1. OCI container per task (Docker/Podman)

One disposable container per agent task: non-root, minimal image, workspace bind, default-deny egress with optional online profile; 1-2 concurrent tasks on small VPS.

**Strengths:**
- Industry tooling
- Clear fs+net knobs
- Matches research pilot default

**Weakest link:** Orchestrator must invoke docker run/podman run consistently; image drift if unpinned

**Risks:**
- Rootful daemon trust if not rootless

**Stepping stone:** yes — opens future possibilities

**Rollback:** Stop using wrapper; run on host with NTM only

### V2. Firejail or bubblewrap profiles

Lightweight namespace sandboxes with profile-as-code; very low RAM vs full images; engineer bwrap argv or Firejail profiles per task class.

**Strengths:**
- Low RAM
- Fast spin-up

**Weakest link:** Hand-built policy; easier to get wrong than Dockerfile discipline

**Risks:**
- Firejail SUID trust model

**Stepping stone:** yes — opens future possibilities

**Rollback:** Disable wrapper scripts

### V3. gVisor or Kata default lane

Stronger syscall or VM isolation per task for untrusted workloads.

**Strengths:**
- Stronger boundaries

**Weakest link:** gVisor syscall overhead; Kata RAM unsuitable as default on 4GB multi-task

**Risks:**
- Ops complexity
- Resource cost

**Rollback:** Revert RuntimeClass / runc default
