# Solutions for: Select Model/Provider pillar for overnight autonomous coding v1

Problem: prob-20260406-006

## Variants (3)

### V1. V1. OpenRouter-first with internal role-policy adapter

Use OpenRouter as the primary provider access layer, with an internal policy contract for role-based routing, typed fallbacks, and budget-pressure behavior. Keep direct-provider clients as emergency fallback path.

**Strengths:**
- Fastest path to multi-provider routing and fallback with low integration overhead
- OpenAI-compatible API surface eases adoption in existing agent stacks
- Enables provider flexibility while centralizing routing behavior

**Weakest link:** Aggregator dependency can become a single operational choke point if escape hatches are not maintained

**Risks:**
- Introduces dependency on aggregator availability and policy/runtime behavior
- Need internal adapter to avoid gateway lock-in over time
- Budget enforcement semantics may remain partly advisory without additional controls

**Stepping stone:** yes — opens future possibilities

**Rollback:** Switch primary traffic to direct providers or a self-hosted gateway while preserving the same internal routing policy contract.

### V2. V2. LiteLLM self-hosted gateway as primary model plane

Run LiteLLM proxy/router as the primary model gateway with explicit role policies, retries, typed fallbacks, provider/model budgets, and observability hooks.

**Strengths:**
- High control over reliability behavior (timeouts/retries/fallback classes)
- Strong budget/routing policy configurability for autonomous workflows
- Reduced dependency on a single managed gateway provider

**Weakest link:** Operational complexity can outweigh benefits for a solo-operator v1 if not tightly scoped

**Risks:**
- Higher operational overhead (deploy/maintain/secure gateway)
- More configuration and runtime complexity for solo operator
- Misconfiguration risk can impact reliability if policy governance is weak

**Stepping stone:** yes — opens future possibilities

**Rollback:** If ops burden is too high, move to managed gateway while retaining policy definitions and telemetry schema.

### V3. V3. Direct-provider abstraction layer (Anthropic/OpenAI/Google)

Build and run an internal abstraction that routes directly across provider APIs with custom retry/fallback/circuit-breaker and budget logic.

**Strengths:**
- Minimal intermediary lock-in and direct access to provider-native features
- Maximum control over fallback and cost semantics
- Clear ownership of reliability logic in-house

**Weakest link:** Engineering and maintenance load is high relative to pilot/v1 velocity needs

**Risks:**
- Highest implementation and maintenance effort
- Longer time-to-stable for unattended overnight reliability
- Greater integration/testing burden across provider-specific API differences

**Rollback:** Adopt gateway layer (managed or self-hosted) if reliability timeline or maintenance burden exceeds solo capacity.
