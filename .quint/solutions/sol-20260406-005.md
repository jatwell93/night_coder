# Solutions for: Select Planner pillar for overnight system v1 (spec-kit vs OpenSpec vs shotgun)

Problem: prob-20260406-005

## Variants (3)

### V1. V1. Spec Kit as dedicated Planner pillar

Adopt spec-kit for constitution/spec/plan/tasks artifacts as the planning system, while keeping Ralph as orchestration runtime. Use planner outputs as execution inputs for overnight runs.

**Strengths:**
- Mature spec-driven workflow with clear phase separation and artifact templates
- Strong task decomposition and acceptance-oriented planning structure
- Large community and broad multi-agent compatibility suggest tooling durability

**Weakest link:** Overhead and rigidity risk for solo operator if planning ceremony is not tightly scoped

**Risks:**
- Can introduce process overhead if all phases are enforced for small scenarios
- Requires adapter conventions to align spec-kit outputs with existing runbook format
- Potential ceremony creep if not constrained to minimal profile

**Stepping stone:** yes — opens future possibilities

**Rollback:** If planning cycle time becomes too high or artifacts are too heavy for unattended loops, fall back to a lighter planner profile or alternate tool while retaining same artifact contract.

### V2. V2. OpenSpec as Planner pillar

Use OpenSpec artifact-guided workflow to generate proposal/spec/design/tasks as planning outputs, optimized for lighter-weight iterative planning.

**Strengths:**
- Cleaner, lighter workflow feel with strong artifact scaffolding
- Supports iterative spec updates without heavy enterprise ceremony
- Good fit for teams wanting flexibility in process strictness

**Weakest link:** Risk of insufficiently structured outputs for fully unattended execution unless conventions are enforced

**Risks:**
- May provide less prescriptive execution structure for unattended overnight handoff compared with stricter frameworks
- Integration conventions with Ralph/OpenJudge pipeline still need explicit definition
- Potential ambiguity in how acceptance checks are serialized for judge consumption

**Stepping stone:** yes — opens future possibilities

**Rollback:** If traceability or task ordering quality is inconsistent, enforce stricter templates or migrate to a more prescriptive planner while preserving artifacts.

### V3. V3. Shotgun as codebase-aware staged planning pillar

Adopt shotgun planning flow to produce codebase-aware specs and staged implementation plans designed to reduce derailment on large feature delivery.

**Strengths:**
- Strong positioning on codebase-aware planning and staged deliverables
- Explicit focus on reducing AI derailment for larger changes
- Could improve quality where deep codebase context is critical

**Weakest link:** Unproven operational fit for your exact autonomous overnight, low-touch workflow constraints

**Risks:**
- Fit for local/headless unattended overnight operation requires validation in your specific constraints
- Potential overlap with orchestration responsibilities if not bounded to planning outputs only
- Smaller ecosystem maturity signal than top alternatives

**Stepping stone:** yes — opens future possibilities

**Rollback:** If headless and integration requirements are not met in trial, revert to a planner with proven CLI/headless behavior.
