# WireMock standalone + WireMock MCP

## 1. Problem Frame

**Signal:** Pilot plan hardcodes Mockoon as DTU fallback without formal comparison against 13+ alternatives surfaced in research (WireMock, Hoverfly, Keploy, MSW, Prism, Mountebank, MockServer, Microcks, etc.). No evidence-based selection exists for the DTU pillar.

**Constraints:**
- Must be free and open-source (budget ~$50 AUD/mo total for all LLM+infra)
- Must run in Docker as a standalone container (out-of-process mock server)
- Must not require kernel-level features (no eBPF dependency) for portability across dev laptop and VPS
- Agent-operable: autonomous coding agent must be able to use the mock without human intervention during overnight runs
- HTTP-first: pilot scenario is GET /api/status returning JSON, but tool must support expanding to multi-route, multi-dependency mocking
- Must work with any language/framework (language-agnostic — agent's code is Python but mock is external)

**Acceptance:** A single DTU tool is selected with documented rationale via Quint decision record; DECISIONS.md DTU row can be filled; pilot compose file and mock data can be created or adapted for the winner.

## 2. Decision

**Selected:** WireMock standalone + WireMock MCP

WireMock is the only DTU candidate with MCP-native agent integration, enabling autonomous agents to create, modify, query, and delete HTTP stubs via tool calls without human intervention. This directly serves the primary optimization target (agent operability) for an overnight autonomous coding system. Additionally: (1) REST Admin API provides a fallback if MCP isn't available in a given agent context, (2) record/replay capability enables future capture of real API traffic for realistic stubs, (3) stateful scenarios support multi-step API interaction testing, (4) massive enterprise community ensures long-term maintenance. The JVM memory cost (~200-400MB) is the acknowledged trade-off, acceptable on a 4GB VPS where DTU is the only JVM workload.

**Invariants:**
- DTU container must be out-of-process: sandbox app connects via UPSTREAM_URL, never in-process interception
- All mock definitions must be reproducible: either committed as mapping files or created via documented API calls in startup scripts
- WireMock Admin API (/__admin) must not be exposed outside the Docker network — agent accesses it, but it must not be reachable from the internet on VPS
- Mock responses must be deterministic for the same request — no external randomness that could cause flaky overnight runs

**Pre-conditions:**
- [ ] Docker and Docker Compose available on target host (laptop or VPS)
- [ ] WireMock Docker image (wiremock/wiremock) pulled or pullable
- [ ] Pilot compose file updated to use WireMock instead of Mockoon
- [ ] WireMock mapping files created for SCN-PILOT-001 (GET /api/status -> {"status":"ok"})

**Post-conditions:**
- [ ] docker compose up starts WireMock serving on port 3000
- [ ] curl http://127.0.0.1:3000/api/status returns {"status":"ok"}
- [ ] WireMock Admin API accessible at http://127.0.0.1:3000/__admin/mappings
- [ ] Existing sandbox app (ping_upstream.py) works without modification against WireMock

**Admissibility:**
- NOT: Must NOT require paid WireMock Cloud subscription — standalone OSS only
- NOT: Must NOT require eBPF or kernel modifications
- NOT: Must NOT introduce JVM tuning that requires Java expertise to operate

## 3. Rationale

| Variant | Verdict | Reason |
|---------|---------|--------|
| WireMock standalone + WireMock MCP | **Selected** | WireMock is the only DTU candidate with MCP-native agent ... |
| Mockoon CLI/Docker | Rejected | No runtime API for dynamic stub management — agent cannot create or modify mocks programmatically during execution. All routes must be predefined in JSON before container start. This is a fundamental limitation for autonomous overnight operation where the agent may need to stub new dependencies it discovers. Mockoon remains a valid stepping stone for manual/simple scenarios but lacks the agent-operability floor needed for our system. |
| Hoverfly (Go proxy/simulate) | Rejected | Proxy-based model (HTTP_PROXY) is architecturally incompatible with our UPSTREAM_URL direct-connection pattern. Adapting would require changing the sandbox app interface contract. Additionally, smaller community and less rich matching than WireMock. Proxy model also risks silent mock bypass if tools don't respect proxy env vars — dangerous for overnight unattended operation. |
| Mountebank (multi-protocol imposters) | Rejected | Dominated by WireMock on agent operability (no MCP), growth path (no record/replay, simpler matching), and community health (fewer recent releases, reduced maintainer bandwidth). Multi-protocol support (TCP, SMTP) is unnecessary for our HTTP-focused use case. The risk of architectural dependency on a less actively maintained project outweighs the marginal resource footprint advantage. |

**Weakest link:** JVM memory footprint — at ~200-400MB idle on a 4GB VPS, WireMock consumes 5-10% of total system RAM; if orchestrator + agent + other containers are also memory-hungry, this becomes the first constraint to hit

**Evidence requirements:**
- Verify WireMock Docker container starts and serves pilot stub within 15 seconds on target hardware
- Verify memory usage stays under 400MB at idle with pilot mappings loaded
- Verify WireMock Admin API can create a new stub via curl POST without container restart
- Verify WireMock MCP server can be installed and connected (stretch goal — document if not yet stable)

## 4. Consequences

**Rollback plan:**
Triggers:
- WireMock memory usage exceeds 500MB idle on pilot hardware
- WireMock MCP proves unusable or abandoned within 3 months
- JVM startup time (>15s) causes timeout failures in automated pilot startup scripts
Steps:
1. Replace WireMock Docker image with Mockoon CLI image in compose file
2. Convert WireMock mapping JSON to Mockoon data file format (manual but straightforward)
3. Update runbook with Mockoon CLI flags instead of WireMock commands
4. Remove any MCP configuration for WireMock
Blast radius: Minimal — only compose files, mock data files, and runbook instructions change; sandbox app and scenarios are unaffected due to UPSTREAM_URL abstraction

**Refresh triggers:**
- Re-evaluate if WireMock MCP is deprecated or unmaintained after 6 months
- Re-evaluate if pilot VPS memory is constrained and WireMock is the bottleneck
- Re-evaluate when non-HTTP mocking needs emerge (gRPC, message queues) — may need to add Mountebank or Microcks alongside WireMock
- Re-evaluate at v2 of the overnight system when mock complexity exceeds WireMock standalone capabilities

**Affected files:** docs/superpowers/pilot/DECISIONS.md, docs/superpowers/pilot/dtu/docker-compose.mockoon.yml, docs/superpowers/pilot/dtu/mockoon-pilot.json, docs/superpowers/pilot/runbooks/PILOT-WEEKEND.md
