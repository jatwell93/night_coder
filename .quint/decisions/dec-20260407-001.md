# OCI container per task (Docker/Podman) with named offline/online profiles

## 1. Problem Frame

**Signal:** Agent tasks need deterministic isolation for shell, filesystem, and network on a solo Linux VPS (~4GB) without Kata-scale RAM cost.

**Constraints:**
- Must work headless overnight
- Budget VPS; avoid VM-per-task as default
- Composable with Ralph + NTM; agent must not escape policy accidentally
- Rollback must be operational not architectural

**Acceptance:** Named execution profiles exist (offline vs online); default path documented; one pilot run completes inside chosen isolation.

## 2. Decision

**Selected:** OCI container per task (Docker/Podman) with named offline/online profiles

Best balance of isolation clarity, solo-operator familiarity, and documented patterns for workspace-only mounts and default-deny egress on a small VPS. Matches web-research pilot recommendation.

**Invariants:**
- Every agent task declares a named execution profile (offline vs online)
- Non-root in container; no privileged mode for pilot
- Workspace-only writable mount unless explicitly justified
- Default-deny egress; online profile documents allowlist

**Pre-conditions:**
- [ ] Docker or Podman available on host
- [ ] Base image pinned in repo

**Post-conditions:**
- [ ] Runbook documents how Ralph (or runner) invokes container per task
- [ ] One successful pilot run inside sandbox

**Admissibility:**
- NOT: Defaulting to host-network or privileged containers for routine tasks
- NOT: Kata-per-task as default on 4GB pilot host

## 3. Rationale

| Variant | Verdict | Reason |
|---------|---------|--------|
| OCI container per task (Docker/Podman) with named offline/online profiles | **Selected** | Best balance of isolation clarity, solo-operator familiar... |
| Firejail or bubblewrap profiles | Rejected | Strong second for RAM; rejected as default because hand-tuned policy error risk is higher for unattended overnight without dedicated hardening time. |
| gVisor or Kata default lane | Rejected | RAM and ops cost dominate on 4GB multi-task host; reserve for exceptional trust boundaries only. |

**Weakest link:** Runner integration: if orchestrator bypasses the wrapper, isolation is void.

**Evidence requirements:**
- Capture resource usage for 1-2 concurrent tasks
- Verify egress deny in offline profile

## 4. Consequences

**Rollback plan:**
Triggers:
- Container startup flakiness blocks overnight completion
Steps:
1. Remove container wrapper from runner
2. Rely on NTM + host execution per prior posture

**Refresh triggers:**
- Multi-tenant or untrusted code becomes default
- VPS upgraded enough for gVisor default
