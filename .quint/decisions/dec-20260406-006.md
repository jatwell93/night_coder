# OpenRouter-first model/provider layer with internal role-policy adapter

## 1. Problem Frame

**Signal:** The project has selected Orchestration (Ralph), DTU (WireMock), Judge (OpenJudge), Observability (Langfuse phased + OpenLLMetry), and Planner (Spec Kit), but has not formally decided the Model/Provider pillar. Current model usage strategy is implicit and ad hoc, with no explicit routing policy by role, no standardized fallback chain, and no enforced cost-governance semantics. This creates risk of budget overruns, inconsistent model quality between phases, and brittle behavior during provider outages in unattended overnight runs.

**Constraints:**
- Must support multi-provider operation and avoid single-vendor lock-in
- Must support headless, non-interactive overnight execution
- Must allow explicit per-role routing policy (e.g., planner/coder/judge)
- Must support fallback behavior for transient failures (rate limits, 5xx, network faults)
- Must support spend governance with clear distinction between advisory alerts and enforced caps
- Must integrate cleanly with existing Ralph + OpenJudge + Langfuse path without replacing orchestration responsibilities
- Must fit pilot/v1 budget constraints and solo-operator complexity limits

**Acceptance:** A single Model/Provider approach is selected with documented rationale, fallback plan, and refresh triggers. In a controlled overnight scenario trial, the chosen approach demonstrates: (1) role-based model routing policy in effect, (2) successful typed fallback on a simulated transient failure, (3) budget controls that trigger expected degradation behavior under threshold pressure, and (4) traceability of routing/cost decisions in observability output.

## 2. Decision

**Selected:** OpenRouter-first model/provider layer with internal role-policy adapter

OpenRouter-first provides the best v1 balance of reliability, speed of integration, and solo-operator feasibility while preserving multi-provider flexibility. It enables immediate role-based routing and fallback behavior with lower upfront effort than self-hosted or fully custom alternatives. The internal policy adapter preserves portability and prevents hard coupling to any single gateway.

**Invariants:**
- Model/provider layer must preserve multi-provider capability and avoid single-vendor lock-in
- Role-based routing policy must be explicit, auditable, and configurable without code rewrites
- Typed fallback behavior for transient failures must exist and be bounded by retry/deadline policy
- Budget controls must distinguish advisory alerts from enforced controls
- Model/provider layer must not replace orchestration responsibilities owned by Ralph

**Pre-conditions:**
- [ ] Role policy table defined for planner/coder/judge/critic paths
- [ ] Fallback/retry/deadline policy documented with failure classes
- [ ] Budget thresholds defined with staged behaviors (notify/degrade/restrict/enforce)
- [ ] Observability mapping defined for route choice, fallback use, retry count, and cost

**Post-conditions:**
- [ ] At least one overnight scenario runs with role-based policy active
- [ ] Simulated transient failure recovers via configured retry/fallback path
- [ ] Budget-pressure behavior triggers expected policy stages in test
- [ ] Routing and cost outcomes are visible in morning review traces

**Admissibility:**
- NOT: NOT: Must not depend on interactive runtime decisions during unattended windows
- NOT: NOT: Must not hide route/fallback decisions from observability output
- NOT: NOT: Must not lock core runtime to a single proprietary provider endpoint
- NOT: NOT: Must not allow unbounded retries or fallback loops

## 3. Rationale

| Variant | Verdict | Reason |
|---------|---------|--------|
| OpenRouter-first model/provider layer with internal role-policy adapter | **Selected** | OpenRouter-first provides the best v1 balance of reliabil... |
| LiteLLM self-hosted gateway as primary model plane | Rejected | Technically strong and on the Pareto front, but higher day-2 operational burden and integration complexity are less suitable for current solo-operator pilot-to-v1 constraints. |
| Direct-provider abstraction layer (Anthropic/OpenAI/Google) | Rejected | Most portable long-term, but implementation and maintenance effort are too high for current v1 delivery timeline and increase near-term reliability risk. |

**Weakest link:** Gateway dependency risk: if OpenRouter availability/policy behavior drifts, unattended runs can degrade unless direct-provider escape paths are kept healthy.

**Evidence requirements:**
- Demonstrate role-based routing policy correctness on representative scenario trace
- Inject transient 429/5xx faults and verify bounded successful recovery
- Demonstrate budget-pressure policy transitions at configured thresholds
- Measure integration effort from baseline to execution-ready configuration
- Verify fallback to direct-provider path in a controlled outage drill

## 4. Consequences

**Rollback plan:**
Triggers:
- Repeated gateway availability incidents impacting overnight completion
- Route/fallback behavior diverges from policy and cannot be corrected quickly
- Budget enforcement behavior proves insufficient for spend containment
- Operational risk from gateway dependency exceeds acceptable threshold
Steps:
1. Promote LiteLLM self-hosted gateway to primary model plane using same policy contract
2. Retain OpenRouter as secondary route where useful
3. Keep direct-provider clients active as hard escape hatch
4. Update DECISIONS.md and runbook mappings, then re-validate evidence requirements
Blast radius: Model-provider configuration, runbooks, and routing telemetry only; orchestration/DTU/judge/observability pillars remain architecturally intact via interface boundaries.

**Refresh triggers:**
- Re-evaluate at pilot retrospective with measured reliability and spend data
- Re-evaluate when scenario count exceeds 5 and routing complexity increases
- Re-evaluate if provider/gateway economics materially change
- Re-evaluate by 2026-10-06 or earlier on repeated outage/failover stress
