# OpenJudge (py-openjudge)

## 1. Problem Frame

**Signal:** The overnight coding loop produces execution traces (logs, git diffs, stdout) that need external validation against holdout scenario specs. Without a dedicated Judge component, the coding agent can declare victory without genuine spec satisfaction. A previous informal selection chose OpenJudge but lacked parity comparison, weakest-link analysis, and tracked rationale.

**Constraints:**
- Python 3.12+ compatible (pip-installable or scriptable)
- Headless CLI invocation — no GUI or web UI required for scoring
- Monthly LLM cost for judge calls under $50 AUD
- No heavy infrastructure (no Postgres, Redis, Celery, K8s required just for judging)
- Must accept arbitrary inputs: scenario markdown text + execution trace text
- Must return structured output: JSON with satisfied (bool), score (0-1), reasoning (string)
- Must support configurable LLM provider — not locked to a single vendor

**Acceptance:** A single Judge tool is selected with: (1) Quint DecisionRecord with full rationale, (2) parity-checked comparison across all 4 candidates from Research_Summary_Table.md §1, (3) weakest-link identified, (4) pilot integration path documented. The selected tool can score SCN-PILOT-001 traces within 60 seconds and under $0.10 per invocation.

## 2. Decision

**Selected:** OpenJudge (py-openjudge)

OpenJudge is the only variant that natively provides the exact abstraction we need: LLMGrader with template variables for scenario+trace input, structured GraderScore output matching our JSON schema, FunctionGrader for deterministic checks, and official Langfuse integration. It scores 5/5 on scenario-trace fit, infrastructure weight, observability integration, LLM flexibility, and extensibility. Its only weakness (maintenance risk at 3/5 due to project youth) is mitigated by high reversibility — falling back to V4 (build-yourself) requires only replacing the grader call with direct OpenAI SDK calls, which is already implemented in pilot_judge.py.

**Invariants:**
- Judge must accept arbitrary text inputs (scenario markdown + execution trace) and return structured JSON
- Judge output schema must contain: satisfied (bool), score (0-1 float), reasoning (string)
- Judge must run headlessly — no GUI or interactive approval required
- Judge must not modify scenario files or execution traces (read-only consumer)
- Scoring a single trace must complete in under 60 seconds and cost under $0.10 AUD

**Pre-conditions:**
- [ ] Python 3.12+ environment available
- [ ] pip install py-openjudge succeeds and imports as 'openjudge'
- [ ] OpenAI-compatible API key available in environment
- [ ] Scenario file (SCN-PILOT-001) and trace file exist at expected paths

**Post-conditions:**
- [ ] pilot_judge.py uses OpenJudge LLMGrader instead of raw openai SDK calls
- [ ] Judge output is valid JSON matching the JUDGE_SCHEMA defined in the plan
- [ ] Langfuse scores are written back via OpenJudge's Langfuse integration
- [ ] pytest test_pilot_judge_output.py passes with mocked OpenJudge grader

**Admissibility:**
- NOT: Judge must NOT require Docker, Postgres, Redis, or any external service beyond an LLM API
- NOT: Judge must NOT be locked to a single LLM provider
- NOT: Judge must NOT store or transmit scenario/trace data beyond the LLM API call
- NOT: Judge must NOT require a web browser or GUI for configuration

## 3. Rationale

| Variant | Verdict | Reason |
|---------|---------|--------|
| OpenJudge (py-openjudge) | **Selected** | OpenJudge is the only variant that natively provides the ... |
| V2. Dify | Rejected | Fails the infrastructure weight constraint (requires Postgres + Redis + Celery + web server for a single post-run scoring call). No Python SDK. Research consensus across multiple sources: 'overkill for a lightweight judge component.' Operationally mismatched — full application platform for a batch scoring task. |
| V3. AgentScope eval framework | Rejected | No pre-built LLM judge implementations. The framework explicitly says users must write their own judge functions. Its own documentation points to OpenJudge as the path to richer judges. Choosing V3 without OpenJudge means reimplementing what OpenJudge already provides. Choosing V3 WITH OpenJudge means V3 adds framework weight without value — just use OpenJudge directly. |
| V4. Build-yourself harness | Rejected | On the Pareto front alongside V1 — dominates on pilot setup effort (already implemented) and maintenance risk (no dependency). However, dominated on extensibility (1 vs 5), observability integration (1 vs 5), and scenario-trace fit (4 vs 5). The extensibility ceiling means scaling from 1 scenario to 10+ requires reimplementing grading abstractions, batch runners, and Langfuse integration that OpenJudge already provides. V4 remains the fallback if OpenJudge is abandoned. |

**Weakest link:** OpenJudge project maturity — young project (2025-2026) with dual GitHub org hosting (agentscope-ai vs modelscope). If the canonical PyPI package name changes or maintainers fragment, we'd need to pin a working version and potentially fork. Mitigation: high reversibility to V4 (build-yourself) which is already implemented.

**Evidence requirements:**
- pip install py-openjudge succeeds on Python 3.12
- Custom LLMGrader with {scenario} + {trace} template returns valid GraderScore
- FunctionGrader wrapping stdout check returns correct score
- Langfuse integration: score appears in Langfuse UI after judge run

## 4. Consequences

**Rollback plan:**
Triggers:
- py-openjudge PyPI package is yanked or renamed
- Breaking API change in LLMGrader or GraderScore that isn't backward-compatible
- Project goes unmaintained for >6 months (no commits, no releases)
Steps:
1. Revert pilot_judge.py to raw OpenAI SDK implementation (V4 baseline — already in plan Task 6)
2. Remove py-openjudge from requirements.txt
3. Update DECISIONS.md Judge row to 'Build-yourself harness (V4 fallback)'
Blast radius: Minimal — only docs/superpowers/pilot/judge/ directory. No impact on Ralph (orchestrator), WireMock (DTU), NTM (leash), or Langfuse (observability).

**Refresh triggers:**
- OpenJudge releases a breaking change to LLMGrader API
- We scale beyond 5 scenarios and need to evaluate batch evaluation performance
- Langfuse releases native judge/eval features that could replace a dedicated judge library
- A new purpose-built 'scenario satisfaction scoring' tool emerges in the ecosystem

**Affected files:** docs/superpowers/pilot/judge/pilot_judge.py, docs/superpowers/pilot/judge/requirements.txt, docs/superpowers/pilot/tests/test_pilot_judge_output.py, docs/superpowers/pilot/DECISIONS.md
