# Spec Kit as dedicated Planner pillar

## 1. Problem Frame

**Signal:** The project has selected Orchestration (Ralph), DTU (WireMock), Judge (OpenJudge), and Observability (Langfuse phased + OpenLLMetry), but no Planner pillar is formally decided. Current planning is partly manual and partly Quint-centered, which risks conflating decision memory with execution planning. Without a dedicated planner, transition from pilot to v1 may suffer from inconsistent task decomposition, weak acceptance traceability, and reduced unattended execution reliability.

**Constraints:**
- Must remain compatible with the chosen Orchestration pillar (Ralph) and must not replace orchestration responsibilities
- Must be open-source or free-to-start for pilot/v1 evaluation and fit overall budget constraints
- Must support machine-usable planning artifacts (spec/plan/tasks/checklists), not just conversational guidance
- Must support headless or CLI-driven usage suitable for overnight automation
- Must preserve provider flexibility and avoid lock-in to a single LLM vendor

**Acceptance:** A single Planner tool is selected with documented rationale and fallback. In a controlled trial, the selected planner can generate a complete plan package for at least one representative scenario (requirements/spec, technical plan, ordered tasks with dependencies, and acceptance criteria) that can be executed by Ralph and evaluated by OpenJudge with minimal manual intervention. Integration overhead and runbook changes are documented, and rollback triggers are defined.

## 2. Decision

**Selected:** Spec Kit as dedicated Planner pillar

Spec Kit provides the strongest combination of complete planning artifacts (spec/plan/tasks), high acceptance traceability, and broad compatibility while still supporting headless usage for unattended overnight workflows. It best matches the need to separate planning from orchestration: Ralph remains the runtime orchestrator, while Spec Kit generates structured executable plans consumed by the existing pipeline.

**Invariants:**
- Planner must generate machine-usable artifacts: specification, technical plan, ordered tasks, and acceptance checks
- Planner must not replace or conflict with Ralph orchestration responsibilities
- Planning outputs must preserve traceability from requirement to task to judgeable acceptance criterion
- Planner workflow must remain provider-flexible and avoid single-vendor lock-in
- Planner adoption must not require paid-only enterprise dependencies for core operation

**Pre-conditions:**
- [ ] Representative scenario selected for planner trial run
- [ ] Adapter contract defined: planner outputs -> Ralph execution inputs
- [ ] Baseline runbook and acceptance schema documented for before/after comparison
- [ ] Local environment and model/provider credentials available for CLI/headless trial

**Post-conditions:**
- [ ] At least one scenario has a complete plan package generated by Spec Kit
- [ ] Generated tasks are executable in overnight flow with minimal manual rewriting
- [ ] Acceptance checks are mapped to OpenJudge-consumable criteria
- [ ] Integration notes and runbook updates are documented

**Admissibility:**
- NOT: NOT: Planner may not assume ownership of orchestration loop control
- NOT: NOT: Planner may not require interactive-only steps during unattended execution window
- NOT: NOT: Planner may not produce opaque outputs that cannot be audited by morning review
- NOT: NOT: Planner may not force a single LLM provider or proprietary runtime as hard dependency

## 3. Rationale

| Variant | Verdict | Reason |
|---------|---------|--------|
| Spec Kit as dedicated Planner pillar | **Selected** | Spec Kit provides the strongest combination of complete p... |
| OpenSpec as Planner pillar | Rejected | Strong and lighter-weight option on the Pareto front, but selected second because it is less prescriptive on execution-structure rigor for unattended handoff unless additional conventions are imposed. |
| Shotgun as codebase-aware staged planning pillar | Rejected | Promising codebase-aware planning approach, but currently higher integration uncertainty and weaker validated headless fit for this exact overnight architecture. |

**Weakest link:** Process overhead creep: if planning ceremony becomes too heavy for solo operation, cycle time can degrade despite higher structure quality.

**Evidence requirements:**
- Trial scenario: generate full plan artifacts and verify completeness against defined artifact checklist
- Measure planning cycle time from scenario prompt to execution-ready task set
- Measure manual rewrite effort required before Ralph can execute generated tasks
- Verify requirement->task->acceptance traceability with at least one end-to-end example
- Verify overnight run can consume planner outputs with no interactive planner step during unattended window

## 4. Consequences

**Rollback plan:**
Triggers:
- Planning cycle time consistently exceeds target threshold for solo workflow
- Generated tasks require substantial manual rewriting before execution
- Headless/non-interactive usage proves unreliable in unattended windows
- Planner-process complexity causes operator fatigue or adoption drop
Steps:
1. Fallback to OpenSpec with stricter template conventions as secondary option
2. Preserve the same artifact contract so downstream components remain unchanged
3. Update DECISIONS.md Planner row and runbook mapping to selected fallback
4. Re-run comparison with updated evidence and record new decision
Blast radius: Planning process and runbook artifacts only; orchestration/DTU/judge/observability pillars remain intact if interface boundaries are preserved.

**Refresh triggers:**
- Re-evaluate at pilot retrospective after first planner-integrated overnight runs
- Re-evaluate when scenario count reaches 5+ and planning throughput becomes critical
- Re-evaluate by 2026-10-06 or earlier if planner ecosystem shifts materially
- Re-evaluate if orchestration interface contract changes and planner integration assumptions break
