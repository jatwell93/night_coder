# mcp-memory-service (sqlite_vec-first) as Memory pillar

## 1. Problem Frame

**Signal:** The system now has formal decisions for orchestration, DTU, judge, observability, planner, and model/provider, but lacks a formal Memory pillar decision. Current continuity relies on logs/artifacts and ad hoc recall, which risks repeated mistakes, weak cross-run learning, and slower diagnosis in unattended overnight execution.

**Constraints:**
- Must be self-hostable or local-first for data control
- Must support headless unattended overnight operation
- Must provide durable cross-run memory with explicit retrieval mechanics
- Must be auditable/inspectable by a human reviewer
- Must not create tight lock-in to a proprietary cloud API
- Must integrate with existing Ralph + OpenJudge + Langfuse + Spec Kit workflow with minimal architecture disruption
- Must fit solo-operator operational capacity

**Acceptance:** A single memory approach is selected with rationale and fallback. In a controlled trial, memory retrieval improves at least one representative overnight scenario by reducing repeated error loops or setup rework, while keeping operational overhead acceptable and outputs auditable for morning review.

## 2. Decision

**Selected:** mcp-memory-service (sqlite_vec-first) as Memory pillar

mcp-memory-service in sqlite_vec local mode provides the strongest v1 balance of useful cross-run retrieval, unattended operation fit, and manageable operational complexity. It is service-native, integrates well with agent workflows, and can be introduced in a constrained local-first profile while preserving future expansion paths.

**Invariants:**
- Memory layer must remain local-first/self-hostable for core operation
- Memory retrieval must be auditable by morning review
- Memory layer must not replace orchestration control or decision authority
- Cross-run recall must materially reduce repeated errors or setup rework
- Memory system must support backup/restore and migration path

**Pre-conditions:**
- [ ] Define minimal sqlite_vec-only deployment profile
- [ ] Define memory write/read policy and retention boundaries
- [ ] Define retrieval points in overnight workflow (when memory is queried/updated)
- [ ] Define backup/restore cadence and test procedure

**Post-conditions:**
- [ ] At least one overnight scenario demonstrates useful cross-run recall
- [ ] Memory artifacts/records are inspectable during morning review
- [ ] Backup and restore test succeeds
- [ ] Operational runbook updated with failure handling and rollback steps

**Admissibility:**
- NOT: NOT: Must not require cloud dependency for baseline operation
- NOT: NOT: Must not hide memory mutations from audit trail
- NOT: NOT: Must not introduce uncontrolled memory growth without lifecycle strategy
- NOT: NOT: Must not create tight coupling that blocks migration to alternative memory backend

## 3. Rationale

| Variant | Verdict | Reason |
|---------|---------|--------|
| mcp-memory-service (sqlite_vec-first) as Memory pillar | **Selected** | mcp-memory-service in sqlite_vec local mode provides the ... |
| Acontext skill-file memory | Rejected | Very strong inspectability and portability on the Pareto front, but selected second because retrieval consistency and integration behavior in this stack require additional validation for unattended runs. |
| Beads as primary memory layer (work graph) | Rejected | Excellent execution-memory/work graph tool, but scope mismatch as sole primary memory pillar because semantic long-term memory needs remain only partially covered. |
| YAMS local content-addressed memory substrate | Rejected | Promising substrate, but explicit experimental maturity warning introduces higher reliability risk for unattended overnight v1 operation. |

**Weakest link:** Configuration/ops sprawl risk: enabling advanced backend features too early can increase complexity and reduce unattended reliability.

**Evidence requirements:**
- Demonstrate reduced repeated failure/setup rework in at least one trial scenario
- Measure retrieval latency and success rate under overnight workload
- Run backup + restore drill and verify data integrity
- Measure integration effort from baseline to stable local deployment
- Run controlled outage/failure simulation and verify graceful degradation

## 4. Consequences

**Rollback plan:**
Triggers:
- Local service instability impacts overnight run completion
- Operational overhead exceeds solo-operator tolerance
- Retrieval quality fails to improve decision/execution outcomes
- Memory growth/maintenance burden becomes unmanageable
Steps:
1. Switch to Acontext as primary fallback memory approach
2. Preserve exported memory artifacts for migration
3. Re-scope Beads as complementary execution-memory if needed
4. Update DECISIONS.md and runbook mappings; re-validate evidence requirements
Blast radius: Memory retrieval and continuity workflows; no direct disruption to orchestration/DTU/judge/model-provider pillars if interfaces remain modular.

**Refresh triggers:**
- Re-evaluate at pilot retrospective using measured retrieval impact
- Re-evaluate when scenario count exceeds 5 and memory volume grows
- Re-evaluate by 2026-10-06 or earlier if memory reliability issues recur
- Re-evaluate if ecosystem maturity shifts materially across top candidates
