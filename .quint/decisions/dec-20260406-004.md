# Langfuse self-hosted with phased deployment (OpenLLMetry instrumentation)

## 1. Problem Frame

**Signal:** The overnight coding loop produces LLM calls, tool invocations, phase transitions, errors, and cost data that nobody monitors in real-time. Morning review currently relies on reading raw orchestrator logs (Ralph events.jsonl) and judge verdicts (OpenJudge JSON). There is no structured trace store, no per-call cost/token visibility, no session-level aggregation, and no UI for browsing execution history. As the system scales beyond the single-file pilot to multi-scenario overnight runs, this gap will make debugging failures, diagnosing cost overruns, and improving agent behavior increasingly difficult.

**Constraints:**
- Must be self-hostable or run fully local — no mandatory SaaS dependency for trace data
- Must not require the coding agent itself to be modified for basic trace capture (instrumentation should wrap, not invade)
- Must support the already-decided stack: Ralph orchestrator, WireMock DTU, OpenJudge judge
- Pilot infrastructure budget: Hetzner CX22 (2 vCPU, 4 GB RAM) shared with Ralph + WireMock + coding agent
- Monthly LLM cost cap: $50 AUD (observability tool must not consume LLM budget unless explicitly opted in)
- Must preserve prompt/response content for post-hoc review (content tracing on by default)

**Acceptance:** 1) A human reviewer can browse overnight traces in under 2 minutes, filter by error/cost, and annotate findings. 2) Per-LLM-call token and cost data is visible without manual calculation. 3) The tool runs on the pilot VPS without starving the agent of resources. 4) Post-pilot: the same tool scales to multi-repo, multi-scenario nightly runs without architectural rework.

## 2. Decision

**Selected:** Langfuse self-hosted with phased deployment (OpenLLMetry instrumentation)

Langfuse is the only candidate that provides a genuine LLM-aware review surface (session grouping, trace trees, per-call cost/token dashboards, annotation). The phased deployment strategy (V5) resolves the Pareto tension between V1's superior morning review and the pilot's 4 GB RAM constraint: Phase 1 uses OpenLLMetry file export for zero-infra trace capture during the pilot; Phase 2 deploys Langfuse on adequate infrastructure and replays pilot traces retroactively. This locks the architectural direction now — Langfuse is the target, not a maybe — while avoiding the risk of ClickHouse OOM-killing the agent on a CX22 VPS. The instrumentation work (OpenLLMetry SDK + @tool decorators) is write-once: identical code serves both the file exporter and the Langfuse OTEL endpoint.

**Invariants:**
- Observability is read-path only: it MUST NOT affect agent execution correctness or timing
- Trace data (including prompt/response content) MUST stay on self-hosted infrastructure — no SaaS telemetry endpoints
- OpenJudge remains the authoritative judge — Langfuse's built-in LLM-as-judge MUST be disabled or clearly labeled 'supplementary' to avoid authority confusion
- OTEL-standard instrumentation: if Langfuse is replaced, the same OpenLLMetry decorators and auto-instrumentation MUST work with the replacement backend (no Langfuse-specific SDK lock-in in application code)

**Pre-conditions:**
- [ ] Ralph orchestrator decided and configured (dec-20260406-001)
- [ ] WireMock DTU running and verified (dec-20260406-002)
- [ ] OpenJudge judge configured (dec-20260406-003)
- [ ] Python 3.12+ environment available for traceloop-sdk installation
- [ ] For Phase 2: dedicated infrastructure with ≥4 GB RAM available for Langfuse stack (separate host or upgraded VPS)

**Post-conditions:**
- [ ] Phase 1 complete: OpenLLMetry SDK installed, LLM calls auto-instrumented, @tool decorators on shell/git commands, OTEL spans exported to /traces/*.otel.jsonl
- [ ] Phase 1 verified: pilot run produces parseable OTEL JSONL files with prompt/response content and token counts
- [ ] Phase 2 complete: Langfuse self-hosted deployment accepting OTEL spans, pilot traces replayed, session-level views functional
- [ ] Phase 2 verified: human reviewer can browse overnight traces in Langfuse UI within 2 minutes, per-call cost visible, annotations saved

**Admissibility:**
- NOT: MUST NOT deploy Langfuse containers on the same 4 GB VPS as the pilot agent during Phase 1
- NOT: MUST NOT use Langfuse Cloud (SaaS) as a shortcut — self-hosted only, per CONSTRAINTS.md data handling requirements
- NOT: MUST NOT instrument code with Langfuse-specific SDK calls — use OpenLLMetry (OTEL-standard) so the instrumentation layer is backend-agnostic
- NOT: MUST NOT enable Langfuse's built-in LLM-as-judge evaluations without explicit agreement on authority boundaries with OpenJudge
- NOT: MUST NOT skip Phase 2 deployment without recording a conscious Quint decision to remain file-based (prevents silent drift to 'good enough')

## 3. Rationale

| Variant | Verdict | Reason |
|---------|---------|--------|
| Langfuse self-hosted with phased deployment (OpenLLMetry instrumentation) | **Selected** | Langfuse is the only candidate that provides a genuine LL... |
| V1. Langfuse self-hosted (full platform, immediate deployment) | Rejected | Non-dominated (Pareto front), but risks pilot failure through infrastructure resource contention. Langfuse's 4-5 container stack (Postgres + ClickHouse + Redis + MinIO + server + worker) consuming ~1.5-2 GB idle RAM on a 4 GB VPS leaves insufficient headroom for the coding agent under load. Selecting V5 preserves V1's full capability while deferring the infrastructure risk to post-pilot, when VPS sizing can be informed by actual trace volumes. |
| V2. OpenLLMetry + Jaeger all-in-one | Rejected | Dominated by V5. V2 requires 1 container (~300 MB RAM) for a generic trace UI that lacks LLM semantics (no cost rollup, no session grouping, no annotation). V5 achieves the same zero-container pilot profile while locking a concrete path to Langfuse's LLM-aware UI. Jaeger is a stepping stone to nowhere useful for LLM observability — you would eventually switch to Langfuse anyway, making V2's Jaeger deployment throwaway work. |
| V3. OpenLLMetry + OTLP file exporter (no backend) | Rejected | Dominated by V5. V3 captures the same OTEL data as V5's Phase 1 but lacks a concrete plan for Phase 2. V5 adds the Langfuse deployment commitment, preventing the 'good enough with files forever' trap. V3's post-pilot scalability is manual-rework; V5's is native-scale. |
| V4. Ralph JSONL only (baseline) | Rejected | Dominated by V3 and V5. Captures no structured LLM data (no per-call tokens, prompts, or cost), making cost diagnosis and quality improvement impossible. Post-pilot scalability is dead-end — Ralph JSONL does not support structured querying across 50-scenario nightly runs. This is not an observability tool; it is a logging side-effect of the orchestrator. |

**Weakest link:** Deferred value during pilot — Phase 1 morning review is file-based (raw OTEL JSON), which means the pilot cannot validate whether Langfuse's UI-driven review experience actually solves the morning review quality problem. The risk is that Phase 2 reveals UI requirements not anticipated from file-based experience. Mitigation: allocate 30 minutes of pilot retrospective specifically to 'what did I wish I could see/filter/annotate that files didn't support?'

**Evidence requirements:**
- Phase 1: verify OpenLLMetry OTEL file traces contain prompt/response content and token counts from at least one pilot run
- Phase 1: measure file sizes produced per overnight run to inform Phase 2 storage requirements
- Phase 2: time a morning review session — can the reviewer identify root cause of a failed scenario within 2 minutes using Langfuse UI?
- Phase 2: verify per-call USD cost is computed and displayed correctly in Langfuse for the LLM provider used
- Post-pilot: compare time-to-diagnosis between file-based review (Phase 1) and Langfuse UI review (Phase 2) on equivalent trace sets

## 4. Consequences

**Rollback plan:**
Triggers:
- Langfuse self-hosted deployment fails to start or is unreliable after 3 attempts
- Langfuse OTEL ingest does not correctly map OpenLLMetry spans (missing prompts, wrong cost data) after SDK version alignment
- Phase 2 infrastructure cost exceeds $20 AUD/month incremental (VPS upgrade or separate host)
- A better LLM-native observability platform emerges that accepts OTEL spans (e.g., OpenLIT, Arize Phoenix) — re-evaluate under same dimensions
Steps:
1. Stop Langfuse containers (if Phase 2 deployed): docker compose down
2. Retain OpenLLMetry instrumentation and switch OTEL exporter to alternative backend (Jaeger, Grafana Tempo, or file)
3. All traces captured during both phases remain in OTEL-standard format — no data loss
4. Update DECISIONS.md to reflect the new observability tool
5. Record a new Quint problem card for the replacement selection
Blast radius: Low. Observability is read-path only. Rollback does not affect agent execution, DTU, judge, or orchestrator. Trace data is preserved in OTEL format regardless of backend. Only the morning review experience degrades temporarily.

**Refresh triggers:**
- Re-evaluate after pilot retrospective — does file-based Phase 1 review reveal unmet needs that change the Langfuse decision?
- Re-evaluate when scaling beyond 5 scenarios — does Langfuse's multi-project model handle the scale, or is a different backend needed?
- Re-evaluate if Langfuse self-hosted resource requirements change significantly in a major version
- Re-evaluate if OpenLLMetry adds a native Langfuse exporter that simplifies or complicates the OTEL path
- Re-evaluate 6 months post-decision (2026-10-06) or when the observability landscape shifts materially
