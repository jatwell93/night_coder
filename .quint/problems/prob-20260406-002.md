# Select DTU/Mocks tool for overnight autonomous coding pilot

## Signal

Pilot plan hardcodes Mockoon as DTU fallback without formal comparison against 13+ alternatives surfaced in research (WireMock, Hoverfly, Keploy, MSW, Prism, Mountebank, MockServer, Microcks, etc.). No evidence-based selection exists for the DTU pillar.

## Constraints

- Must be free and open-source (budget ~$50 AUD/mo total for all LLM+infra)
- Must run in Docker as a standalone container (out-of-process mock server)
- Must not require kernel-level features (no eBPF dependency) for portability across dev laptop and VPS
- Agent-operable: autonomous coding agent must be able to use the mock without human intervention during overnight runs
- HTTP-first: pilot scenario is GET /api/status returning JSON, but tool must support expanding to multi-route, multi-dependency mocking
- Must work with any language/framework (language-agnostic — agent's code is Python but mock is external)

## Optimization Targets

- Agent operability — how easily can an autonomous agent create, modify, and interact with mocks programmatically
- Growth path — ability to expand from simple pilot stubs to complex multi-service mock environments without tool migration
- Operational simplicity — minimal setup, single container, fast startup, low resource footprint

## Observation Indicators

- Mock fidelity to production APIs (good enough for pilot; contract testing comes later)
- Community size and release cadence (don't optimize for popularity, but watch for abandonment risk)

## Acceptance

A single DTU tool is selected with documented rationale via Quint decision record; DECISIONS.md DTU row can be filled; pilot compose file and mock data can be created or adapted for the winner.

## Blast Radius

Small — pilot only. Swapping mock containers touches compose files and mock definitions, not application code. UPSTREAM_URL abstraction isolates the sandbox app.

## Reversibility

high
