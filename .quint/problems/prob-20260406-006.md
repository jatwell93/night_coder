# Select Model/Provider pillar for overnight autonomous coding v1

## Signal

The project has selected Orchestration (Ralph), DTU (WireMock), Judge (OpenJudge), Observability (Langfuse phased + OpenLLMetry), and Planner (Spec Kit), but has not formally decided the Model/Provider pillar. Current model usage strategy is implicit and ad hoc, with no explicit routing policy by role, no standardized fallback chain, and no enforced cost-governance semantics. This creates risk of budget overruns, inconsistent model quality between phases, and brittle behavior during provider outages in unattended overnight runs.

## Constraints

- Must support multi-provider operation and avoid single-vendor lock-in
- Must support headless, non-interactive overnight execution
- Must allow explicit per-role routing policy (e.g., planner/coder/judge)
- Must support fallback behavior for transient failures (rate limits, 5xx, network faults)
- Must support spend governance with clear distinction between advisory alerts and enforced caps
- Must integrate cleanly with existing Ralph + OpenJudge + Langfuse path without replacing orchestration responsibilities
- Must fit pilot/v1 budget constraints and solo-operator complexity limits

## Optimization Targets

- Maximize unattended run reliability through robust routing and failover
- Minimize total cost variance while preserving quality on critical phases
- Reduce operational and integration complexity for a solo operator

## Observation Indicators

- Provider marketing claims and model leaderboard position changes
- Community star growth of provider/gateway ecosystems
- Breadth of optional enterprise features not required for v1

## Acceptance

A single Model/Provider approach is selected with documented rationale, fallback plan, and refresh triggers. In a controlled overnight scenario trial, the chosen approach demonstrates: (1) role-based model routing policy in effect, (2) successful typed fallback on a simulated transient failure, (3) budget controls that trigger expected degradation behavior under threshold pressure, and (4) traceability of routing/cost decisions in observability output.

## Blast Radius

Execution reliability and cost behavior across all overnight runs; touches orchestration configuration, runbooks, and provider credential management. Downstream pillars remain intact if interface boundaries are respected.

## Characterization v1 (2026-04-06)

| Dimension | Role | Scale | Unit | Polarity | Measurement |
|-----------|------|-------|------|----------|-------------|
| Role-based routing fidelity | target | ordinal | 1-5 score | higher_better | Define expected model assignment for planner/coder/judge/critic and run a representative scenario. Score by percentage of calls routed to intended role policy with correct fallback precedence. 1=frequent misroutes, 5=consistent policy adherence. |
| Transient-failure failover success | target | ratio | % successful recoveries | higher_better | Inject transient faults (429, 5xx, timeout/network interruption) in controlled tests. Measure percentage of requests that recover via retries/fallback within configured deadline without manual intervention. |
| Budget control enforceability | target | ordinal | 1-5 score | higher_better | Test advisory thresholds and enforced caps separately. Score whether policy stages (notify, degrade, restrict, block) trigger as designed under simulated budget pressure and whether behavior is auditable. |
| Cost variance under fixed workload | target | ratio | coefficient of variation | lower_better | Run repeated equivalent workloads and compute spend variance. Lower variance indicates more predictable economics for unattended runs. |
| Integration effort with existing pillars | target | ratio | person-hours | lower_better | Estimate and validate effort for configuration, adapter wiring, runbook updates, and telemetry mapping into Ralph/OpenJudge/Langfuse path using a timeboxed integration spike. |
| Operational overhead (solo operator) | target | ordinal | 1-5 score | lower_better | Assess day-2 effort: deployment, incident handling, key management, policy changes, and drift management. 1=very low overhead, 5=high ongoing burden. |
| Provider/runtime portability | target | ordinal | 1-5 score | higher_better | Verify ability to swap providers and/or gateway layer with minimal changes to internal policy contract and runtime adapters. Must pass minimum threshold to be admissible. |
| Ecosystem maturity signal | target | ordinal | 1-5 score | higher_better | Track release cadence, issue responsiveness, and documentation quality. Use as risk context only, not direct optimization. |

**Parity rules:** All variants must be tested against the same representative overnight scenario, same role policy definitions, same budget thresholds, same timebox, and same evaluator rubric. Keep model quality tier comparable across variants where possible. Use identical fault-injection cases and identical observability collection. Do not alter scenario prompts per variant beyond minimal adapter necessities; record any unavoidable differences explicitly.
