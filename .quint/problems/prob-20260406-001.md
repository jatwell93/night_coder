# Select orchestration tool for overnight autonomous coding (Attractor pillar)

## Signal

Ten orchestration candidates have been researched across the Attractor pillar (OpenHands, AG2, Deer Flow, CrewAI, AgentFlow, Gas Town, oh-my-openagent, Ralph, Ruflo, Agent Flywheel). We need to select one tool to serve as the orchestration spine for an autonomous overnight coding loop on a budget VPS. The choice constrains runbook format, trace output, pillar integration patterns (Judge, DTU, Leash, Observability), and cost profile. A wrong pick wastes the pilot weekend and creates downstream rework across all five pillars.

## Constraints

- Total monthly spend <$150 AUD (VPS + LLM combined)
- No OpenAI-only provider lock-in — must support Anthropic, Google, DeepSeek, or OpenRouter
- Must run headless/unattended for up to 10 hours on a single budget VPS (e.g. Hetzner CX22, 4GB RAM)
- Must be BYO-API-key — no mandatory commercial CLI subscription (Claude Max, Cursor Pro, etc.)
- Must not prevent integration with external Judge, DTU, Leash, and Observability pillars
- Framework/orchestrator itself must be free/OSS (MIT, Apache-2, etc.)
- Must produce file-based traces readable without proprietary SDKs for morning human review

## Optimization Targets

- Overnight reliability: crash recovery, rate-limit resilience, graceful degradation over 10h unattended
- Morning reviewability: structured traces readable by a human at 7am without re-running anything
- Time-to-first-pilot: can execute a real overnight run this Saturday, not in 3 weeks

## Observation Indicators

- Parallelism capability (not needed for single-scenario pilot, but watch for v2 multi-repo expansion)
- Community ecosystem velocity (GitHub activity, maintainer responsiveness, issue resolution pace)
- Context drain resistance over long runs (accumulating vs fresh-per-cycle architecture)

## Acceptance

A single orchestrator is selected with documented rationale. Decision includes rollback plan (fallback orchestrator identified), refresh triggers, and evidence requirements for post-pilot measurement.

## Blast Radius

Medium — pilot branch is disposable, but orchestrator choice shapes runbook, trace format, and all future pillar integration code. Switching orchestrators later means rewriting Judge/DTU/Leash integration points.

## Reversibility

medium

| Dimension | Role | Scale | Unit | Polarity | Measurement |
|-----------|------|-------|------|----------|-------------|
| crash_recovery | target | ordinal | capability level | higher_better | None (die and lose state) / Manual-restart (files survive on disk, re-run manually) / Event-replay (auto-resume from crash point via event log) |
| resource_footprint | target | ordinal | RAM class | lower_better | Light (<500MB orchestrator overhead) / Medium (500MB-1.5GB) / Heavy (>1.5GB, Docker-in-Docker or JVM) |
| time_to_first_run | target | ordinal | effort class | lower_better | Minutes (clone+configure, documented quick-start) / Hours (install+configure+test, some troubleshooting expected) / Days (significant integration coding, custom glue, unstable tooling) |
| native_safety_limits | target | ordinal | capability level | higher_better | None (no built-in caps, fully trust-the-agent) / External-only (wrap with timeout/budget scripts) / Native (max_cost, max_iterations, max_runtime built into orchestrator config) |
| trace_output_quality | target | ordinal | structure level | higher_better | Opaque (binary/proprietary, not parseable) / Logs (text grep-able, unstructured) / Structured-events (JSON/JSONL, parseable by external judge and observability tooling) |
| model_flexibility | target | ordinal | provider breadth | higher_better | Single-provider-locked (one vendor CLI dependency) / Multi-provider (2-3 configurable backends) / Any-via-adapter (LiteLLM/OpenRouter style, 100+ providers) |
